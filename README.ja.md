# ebpy

[English](README.md) | 日本語

既存の Python コードベースを、**良くなる一方**にする。

[ever-better](https://github.com/isamu/ever-better) の Python 版です。考え方もフェーズも同じで、
ESLint / TypeScript の代わりに Ruff / mypy / pytest を土台にしています。

リポジトリに足りない品質ツールを報告し、導入し、**今日時点の違反をすべて上限（天井）として記録**
します。そのコミット以降、既存コードは既得権として見逃され、新しいコードにはルールセット全体が
適用されます。天井は下がることはあっても、上がることはありません。

## なぜ必要か

古いリポジトリに厳しい linter を入れると 4000 件のエラーが出て、結局 revert されます。よくある
回避策 — 全部を warning にする — では何も強制されず、件数は静かに増えていきます。

ESLint はこれを **bulk suppressions** で本体解決しました。Ruff に同等の機能はないため、ebpy が
ラチェット機構そのものを持ちます。`freeze` が**ファイルごと・ルールごと**の違反数を記録し、
`check` がそれを超えた分で失敗し、`prune` だけがその数字を下げられます。既存の 1 行も変えずに、
初日から全ルールをエラーにできます。

これは linter ではありません。**あなたの** Ruff を、**あなたの**設定で、**あなたの** virtualenv
から実行します。

## インストール

```bash
uv add --dev ebpy      # または pip install ebpy / pipx install ebpy
```

Python 3.11 以降。uv / poetry / pdm / pipenv / pip に対応し、パッケージマネージャは lockfile から
検出されます。生成される CI ワークフローも検出したものを使います。

## CLI を直接使う

```bash
ebpy diagnose     # 読み取り専用: 何が足りないか、その不足が何を意味するか
ebpy bootstrap    # 導入して設定ファイルを生成
ebpy freeze       # 今日の違反を天井として固定
ebpy check        # CI ゲート: 何かが増えていたら失敗
ebpy next         # どこから潰すべきか、その 1 手が何を強制できるようにするか
ebpy report       # 違反の分布を markdown で（CI のジョブサマリ向け）
ebpy secrets      # 履歴全体をスキャンして混入した認証情報を探す
ebpy prune        # 修正後: 取り戻した天井を回収する
ebpy catalog      # 既存のヘルパー一覧（6 個目の同じ関数を書かせない）
ebpy log          # 何をしたかを、現在のコミット付きで記録
```

## Claude Code にリポジトリを渡す

[`skills/`](skills) にあるスキルがもう半分です。CLI は決定的にできること（検出・導入・計測・描画・
ゲート）を担当し、スキルは判断が要ること — この違反は本物のバグか、修正ではなく issue にすべきか、
どこで手を止めて聞くべきか — を担当します。プロジェクトの `.claude/skills/` にコピーして、こう
言うだけです。

```
このリポジトリに ebpy を回して
```

| 言い方 | 動くもの |
| --- | --- |
| 「ebpy を回して」「このリポジトリを綺麗にして」 | 全工程を自動で — `ebpy-run` |
| 「ここで ebpy は何をする?」 | 診断して 1 フェーズずつ案内 — `ebpy-guide` |
| 「lint を入れて」 | `ebpy-bootstrap` |
| 「ベースラインを固定して」 | `ebpy-freeze` |
| 「リファクタリングして」 | `ebpy-drain` |

## 各コマンドの説明

### `diagnose`

読み取り専用の調査。パッケージマネージャ、宣言された Python バージョン、フレームワーク、
Ruff / フォーマッタ / mypy / pytest / vulture / pre-commit / シークレットスキャンの有無、CI が何を
どのプラットフォームで実行しているか、ワークフローの `uses:` がすべてコミット SHA に固定されて
いるか、サイズ上限を超えたファイル数、そして各不足を解消するフェーズ付きのギャップ一覧を
報告します。

`--write` で `QUALITY.md` と `.ebpy/state.json` を永続化。`--json` で生の診断結果。

検出は**インストール状況ではなく設定**を読みます。設定されていないツールは何も強制しませんし、
設定だけあってインストールがなければ初回実行で派手に失敗して気付けるからです。

### `bootstrap`

リポジトリ自身のパッケージマネージャで不足している開発依存を導入し、互いに見えないものを補い合う
層を生成します。

| 層 | ツール | 見えるもの |
| --- | --- | --- |
| 関数のサイズと複雑度 | Ruff `C90`, `PL` | 長すぎる関数、深いネスト、分岐過多 |
| バグのパターン | Ruff `F`, `B`, `SIM` | ミュータブルなデフォルト引数、遅延束縛、未定義名 |
| 型 | mypy `strict` | lint ルールでは届かないエラー |
| スタイル | `ruff format` | 一度決めれば、以後どの diff でも争わない |
| デッドコード | vulture | 誰も呼んでいない関数やクラス |

加えて 3 プラットフォームの quality ワークフロー、シークレットスキャンのワークフロー、
`dependabot.yml`、`.gitattributes`。ワークフロー内の Action はすべて完全なコミット SHA に固定し、
リリース名は末尾コメントとして併記します。gitleaks のダウンロードもダイジェストで検証します。
タグは所有者がいつでも別のコードへ動かせますし、リリースアセットも同じタグのまま差し替えが
可能だからです。ebpy が見なくなった後にその固定が古びないようにするのが Dependabot の役割です。

**既存の設定は決して上書きしません** — そこにある例外には、ファイルに書かれていない理由が
あるからです。`--dry-run` は計画を表示するだけで何も触りません。

### `freeze`

Ruff を実行し、今日のファイル別ルール別の件数を `.ebpy/baseline.json` に書き、mypy のエラー総数を
ラチェット付きカウンタとして記録し、`QUALITY.md` を描画します。3 つまとめてコミットしてください。

2 回目の実行は拒否されます。それ以降に増えた分まで既得権にしてしまうからです。天井を下げるには
`prune` を、ルールを本当に設定変更したなら `--force` を使ってください。

**構文エラーは凍結せず報告します。** パースできないファイルはどのルールからも見えないので、件数を
記録するのは嘘になります。freeze はファイル名を挙げて、先に直すよう促します。

### `check`

CI ゲート。あるファイルのあるルールの違反数がそのセルの上限を超えたとき、または mypy カウンタが
増えたときに失敗します。lint の後にワークフローへ追加してください。

ラチェットは**ファイル単位かつルール単位**で、リポジトリ全体の合計より厳しくなります。新しい
ファイルには自分のセルがないので、そのルールの全体件数が変わっていなくても最初の 1 件で失敗します。

### `next`

```bash
ebpy next
ebpy next --json
ebpy next --fan-in
```

推測ではなく計算された消化順。ラチェットがファイル別ルール別に効くため、有用な問いは「どのルールが
一番少ないか」ではなく「**どの 1 手が一番多くを強制できるようにするか**」です。4 つのリストで
答えます。

| セクション | 用途 |
| --- | --- |
| take these first | あと 1〜2 件でクリーンなファイル。1 手でそのファイルのそのルールが恒久的に強制される |
| rules by files to touch | 3 ファイルに 40 件と 31 ファイルに 38 件は `status` では同じ大きさで、作業量は 10 倍違う |
| the last files carrying a rule | 誰も終わらせなかったディレクトリの残り |
| leave these until last | その件数は backlog ではなく再設計 |

報告しているのは「そのルールを**まだ抱えている**最後のファイル」であって、「そのディレクトリの
残りはクリーン」という主張ではありません。Ruff が一度も見ていないファイルにもセルはなく、
ベースライン上の計算だけでは両者を区別できないからです。

`--fan-in` は各行に「そのファイルを import しているファイル数」を足します。「これはどれくらい
大変か」のもう半分は「修正がどこまで波及するか」だからです。リポジトリ内の**全ソースファイルを
パース**するのでデフォルトではなくフラグです。そして**並び順は一切変えません**。fan-in は*型*の
修正を高くしますが、`C901` については何も語りません — そちらは何ファイルから import されていようと
修正は局所的だからです。

### `report`

markdown で、backlog を **ルール × 領域**の表として出します。負債の大きさだけでなく形が見えます。
標準出力に書き、`$GITHUB_STEP_SUMMARY` が設定されていればそこに**追記**します。これにより、誰も
ワークフローを編集しなくても CI レポートになります。生成されるワークフローは `check` の後に
`if: always()` で実行します — ゲートが落ちた実行こそ、backlog が最も価値を持つ実行だからです。

**これは決してゲートではありません。** 終了コードを変えませんし、サマリファイルに書けなくても
失敗しません。Ruff がまったく動かない場合は `.ebpy/baseline.json` にフォールバックし、その旨を
明記します — 「負債なし」と「誰も負債を見ていない」が同じ見た目になってはいけません。

### `secrets`

`gitleaks` を**履歴と作業ツリーの両方**に対して実行し、何か見つかれば失敗します。

両方を走らせるのは、片方だけではシークレットを抱えたリポジトリを通してしまうからです。履歴の
スキャンは 1 時間前に貼り付けてまだコミットしていない鍵を見逃し、作業ツリーのスキャンはコミット後に
削除された鍵 — すべてのクローンに残っている鍵 — を見逃します。

**ここだけはベースラインを持ちません。それがこの機能の要点です。** 他のすべてのルールは現状を記録
して線を保ちますが、コミットされた鍵はすでに公開済みなので、既得権にするものは何もなく、修正は
コミットではなくローテーションです。

gitleaks は指定しない限り「見つけた」と「実行できなかった」を同じ終了コードで返すため、答えは 2 つ
ではなく 3 つです。

| | |
| --- | --- |
| クリーン | exit 0 |
| シークレット検出 | exit **2**（内容は redact 済み） |
| **スキャンを実行できなかった** | exit **1** — クリーンな結果ではないと明示 |

最後の行は見た目以上に重要です。git 作業ツリーの外で `gitleaks git` はエラーを記録しつつ
**0 コミットをスキャン**して exit 0 と "no leaks found" を返します。何も読まなかったスキャンに
対する健康証明書です。ebpy はこれを拒否します。

### `prune`

既得権化された違反を修正すると、そのセルは古くなります。`prune` はすべてのセルを「今も存在する
数」まで下げ、修正した分だけを正確に回収します。減らすことしかできないため、いつ実行しても安全で、
**天井が下がる唯一の方法**です。

### `log`

```bash
ebpy log --kind drained  --rule C901 "6 件中 1 件は本物のバグだった"
ebpy log --kind deferred --rule PLR0915 "router.py は 1400 行。単独プロジェクト級"
ebpy log --kind issue    --rule B008 "#42 を作成 — プロダクト判断"
```

何が起きたかを現在のコミットとともに記録します。`QUALITY.md` の **Work log** を書くのはこれだけ
です — 他のコマンドは件数しか記録せず、理由は記録しません。真価を発揮するのは `deferred` で、
見つけた時点のコミット付きで **Carried over** チェックリストに描画されます。「router.py は分割が
必要」というメモは、それがいつ真だったのか分からなければ、400 コミット後には無価値だからです。

### `catalog`

`docs/shared-helpers.md` を書きます。すべての公開関数を、ディレクトリごとに、docstring の最初の
一文とともに列挙します。CLAUDE.md からここを参照させてください。

2 つのスキャンの隙間を埋めます。linter は 1 ファイルの内側しか見ず、重複検出はテキストが似て初めて
コピーに気付きますが、独立に書かれた 2 つの実装が似ていることは稀です。「6 個目の同じ関数が 6 個目
の名前で書かれた」ことを報告できるのは、これだけです。

### `status`

現在のフェーズ、backlog、残件数の少ないルールを表示します。診断が 30 日以上前、50 コミット以上
遅れている、あるいはこの履歴にもう存在しないコミット（rebase や force-push）で取られた場合は、
先頭に `STALE` 行が付きます。ラチェット自体は古くなりません — Ruff が常に現在のツリーに対して
維持するからです — が、ギャップ一覧、ファイルサイズ、deferred メモは古くなります。

## 成果物

| ファイル | 所有者 | コミットするか |
| --- | --- | --- |
| `.ebpy/baseline.json` | ebpy | する — これ自体が天井 |
| `.ebpy/state.json` | ebpy | する — 台帳 |
| `QUALITY.md` | 台帳から描画 | する — 人間向けのビュー |

`QUALITY.md` は毎回再生成され、台帳から描画された 4 つのセクションを持ちます。フェーズを
チェックボックスにした **Worklist**（残件の少ないルールを子項目に）、意図的に見送った
リファクタの **Carried over**、**Ratchet** テーブル、そして **Work log**。
`<!-- ebpy:notes:start -->` マーカーの間に書いたものは再描画後も残ります。

## フェーズ

| フェーズ | 内容 |
| --- | --- |
| P0 diagnose | 調査し、すべての不足に名前を付ける |
| P1 bootstrap | 導入し、設定を生成する |
| P2 freeze | 天井を固定し、CI をゲートする |
| P3 drain | 1 ルールずつ潰す。見つけたバグにはテストを付ける |
| P4 tighten | 次のルール階層を追加して繰り返す |
| P5 split & DRY | 重複とデッドコードを消す |

価値があるのは P3 と P5 で、ここは**既定で自動化**されます。修正、関数の抽出、テストの追加、孤児
ファイルの削除は、聞かずにやります。所有者の判断が要るリファクタだけが GitHub issue になり、その
issue には選択肢と、エージェントならどれを選ぶかが書かれます。

## ever-better との違い

逐語移植ではありません。考え方は同じで、機構は Python エコシステムに従います。

- **ラチェットは ebpy 自身のもの。** ESLint には `--suppress-all` がありますが Ruff にはないため、
  `freeze` / `check` / `prune` がファイル別ルール別の台帳を直接実装しています（ファイル形式は
  ESLint と同じ形）。
- **mypy はベースラインではなくカウンタ。** 型エラーにはファイル単位の抑制機構がないので、
  ever-better が ESLint の warning を扱うのと同じやり方で総数をラチェットします。
- **構文エラーは数えず、名指しする。** Ruff はこれをルール名なしの `invalid-syntax` として報告
  します。既得権化できないので、freeze も check も 0 を記録せずに拒否します。
- **fan-in は Python の import を解決します** — 相対、絶対、`src/` レイアウトの両方。
- `migrate` と `emit-diff` はありません。JavaScript → TypeScript に相当するものが Python には
  なく、「型だけのリファクタが挙動を変えていない」ことを証明できるコンパイル出力もないためです。

## 設計

エージェントが実行のたびに遅く、あるいは違うやり方でやってしまうことは CLI に。markdown の
チェックリストで表現できないことはスキルに。

ランタイム依存はゼロ。
